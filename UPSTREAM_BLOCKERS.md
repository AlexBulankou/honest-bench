# Upstream blockers — active asks only

Active upstream blockers that need action now, ordered **substrate-first** (substrate is the primary product: private GA in September, public GA in October; the sandbox runtime moves to maintenance mode). Completed and superseded items live in **[Recently landed](#recently-landed-archive)** and are dropped on the next refresh — this page stays work-to-do-only by standing discipline.

**How to read this page.** Each product has one table. The **Fix status** column is the at-a-glance disposition (controlled vocabulary below); the **Upstream / workaround** column gives the customer the immediate mitigation and the durable upstream fix in one place. Engineering depth for every item — SHA bisects, fire-by-fire timelines, per-lever measurements — lives in [**UPSTREAM_BLOCKERS_DETAIL.md**](UPSTREAM_BLOCKERS_DETAIL.md). Machine-readable link states: [`render/upstream_links.json`](render/upstream_links.json), updated in the same commit as any state change here and re-swept against the public GitHub API on each refresh.

**Fix-status vocabulary:** `upstream-merged` (durable fix already merged upstream) · `adopt-on-merge` (fix in flight upstream; adopt on the integration fork when it lands) · `fork-validated · upstream-pending` (fix built and proven from a fork build; durable upstream fix still pending) · `no-patch-warranted` (an existing upstream primitive already suffices — dated reason given) · `n/a (no fork)` (not an OSS repo; outside the fork-fix model).

**Engagement model:** upstream approvers are engaged through existing maintainer relationships. We do not open new issues/PRs upstream; reference patches are staged on integration forks, validated from fork builds, and offered only if a maintainer asks.
